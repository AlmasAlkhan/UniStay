# UniStay mobile

Мобильная часть Турара Нурбаули: Flutter-клиент общего Django REST API UniStay. Основной пользователь — студент. Интерфейс на русском языке. Backend находится в соседней папке `backend`; приложение не создаёт собственную базу объявлений.

## Реализованные сценарии

- Просмотр каталога без регистрации; поиск, город, район, университет, диапазон цены, свободные места, сортировка и постраничная загрузка.
- Карточка квартиры: фотографии, условия, стоимость места, залог, дата заселения, вместимость и доступный сервером адрес.
- Регистрация студента, вход, выход с отзывом серверной сессии, восстановление сессии из защищённого хранилища.
- Подтверждение email и восстановление пароля через вставку ссылки из письма; повторный запрос письма.
- Профиль: университет, описание, режим сна, курение, чистоплотность, согласие на показ анкеты.
- Просмотр доступных анкет соседей и объяснение сравнения привычек.
- Подача заявки, список заявок, история, отмена. Аккаунт владельца может войти, увидеть и принять/отклонить входящие заявки; создание объявлений в мобильный объём не включено.
- Загрузка, пустые результаты, ошибки API/сети, повтор запроса, защита от повторного нажатия, обновление жестом и настройка адреса сервера.

Сервер проверяет права, подтверждение email, заполнение профиля, число мест и допустимость переходов статусов. Клиент показывает предварительные подсказки, но не подменяет серверные проверки. Отправленная заявка не означает занятое место: это происходит после принятия владельцем.

## Запуск

Требуется Flutter с Dart 3.11 или совместимой более новой версией. Зависимости зафиксированы в `pubspec.lock`.

```powershell
cd mobile
flutter pub get
flutter run -d <device-id> --dart-define=API_BASE_URL=https://your-api.example.com
```

`API_BASE_URL` — корень сервера, без `/api/v1`. Адрес можно поменять в приложении через кнопку настроек. При смене хоста токен не переносится. Сохранённый в настройках адрес имеет приоритет над параметром сборки. Для release требуется HTTPS; без параметра сборки используется заглушка `https://api.example.com`, которую нужно заменить в настройках перед входом.

Локальные варианты для debug:

| Клиент | Адрес backend |
| --- | --- |
| Android Emulator, backend на этом Windows-компьютере | `http://10.0.2.2:8000` (по умолчанию) |
| Chrome на компьютере backend | `http://127.0.0.1:8000` (по умолчанию) |
| Физический телефон или backend на Mac Алмаса | Доступный LAN-адрес компьютера backend, например `http://192.168.1.10:8000` |

`127.0.0.1` на телефоне указывает на сам телефон. Для LAN сервер должен слушать внешний интерфейс, firewall должен разрешать доступ, а `ALLOWED_HOSTS` Django — содержать адрес сервера. В текущем Compose Алмаса порт может быть привязан только к loopback; это необходимо согласованно изменить на его машине. Для iOS предпочтителен HTTPS: ATS-исключения для незащищённых соединений не добавлены.

Для локального браузерного просмотра:

```powershell
flutter run -d chrome --web-port=3000 --dart-define=API_BASE_URL=http://127.0.0.1:8000
```

В backend `CORS_ALLOWED_ORIGINS` должен включать `http://localhost:3000` (это уже предусмотрено настройками по умолчанию). Web-хранилище работает на localhost или HTTPS. На Android используется защищённое хранилище устройства, на iOS — Keychain. Пароль не сохраняется.

## Подтверждение почты

По текущим настройкам backend письма выводятся в серверную консоль. Для локальной проверки возьмите ссылку из вывода Django и вставьте её на экране подтверждения или восстановления. Приложение принимает полный URL, не выполняя переход на его хост. Автоматическое открытие приложения по email-ссылкам ещё не настроено. Для реальных пользователей необходим SMTP на стороне сервера.

## Проверки

```powershell
flutter analyze
flutter test
flutter build apk --debug
flutter build web --dart-define=API_BASE_URL=https://your-api.example.com
```

Unit/widget-тесты проверяют Bearer-авторизацию, обработку серверных ошибок, восстановление и истечение сессии, изоляцию токена между серверами, фильтры, ограничение неподтверждённых аккаунтов и путь подачи/отмены заявки. Данные в этих тестах синтетические.

Отдельный интеграционный сценарий запускает настоящий Django, создаёт временные SQLite и media, затем вызывает API из Dart. Запуск из корня репозитория после установки Python-зависимостей backend:

```powershell
backend\.venv\Scripts\python.exe mobile\tool\check_backend.py
```

Он проверяет вход двух ролей, профиль, загрузку фото, публикацию, поиск, скрытие адреса, заявку, повторную заявку (409), принятие, соседей, отмену, освобождение места, историю и отзыв сессии. Рабочая база и `.env` не меняются. Это последовательная интеграционная проверка; она не подтверждает конкурентную работу PostgreSQL или доступность сервера на Mac Алмаса.

Снимок интерфейса с тестовыми данными для локальной проверки:

```powershell
flutter test tool/preview_test.dart
```

Изображение сохраняется в игнорируемую папку `.local`. В runtime приложения демонстрационные данные не используются.
На Windows предпросмотр использует системный Segoe UI; на других ОС задайте `PREVIEW_FONT` как путь к TTF со знаками кириллицы. При нестандартном расположении Flutter задайте `FLUTTER_ROOT`.

## Структура

| Файл | Назначение |
| --- | --- |
| `lib/data.dart` | HTTP API, серверные ошибки, сессия и защищённое хранилище |
| `lib/main.dart` | Тема, навигация, инициализация |
| `lib/catalog.dart` | Поиск, фильтры, карточка, соседи, отправка заявки |
| `lib/account.dart` | Вход, регистрация, профиль, почта, пароль, адрес API |
| `lib/applications.dart` | Заявки, история и смена статуса |
| `lib/widgets.dart` | Общие элементы интерфейса |

## Границы версии

Оплаты, договоры, чат, отзывы, push, офлайн-каталог и создание объявлений владельцем не входят в мобильную версию этого этапа. Статусы обновляются по жесту, кнопке или после действия, без фонового realtime. Фото поступают с backend; локальная конфигурация Django обслуживает media при `DEBUG=true`, production-хранилище настраивается отдельно.

Android debug APK предназначен для разработки. Release signing в сгенерированном Android-проекте ещё использует debug key и должен быть настроен перед распространением. iOS-проект подготовлен, но его сборка и подпись требуют macOS/Xcode. Тесты на устройстве, доставка настоящих писем и проверка общего сервера команды — отдельный этап интеграции.
